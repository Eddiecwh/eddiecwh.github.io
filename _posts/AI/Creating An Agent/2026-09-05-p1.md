At CYC 26 this year, there were a lot of talks on AI - specifically regarding Agents, and the steps that we must undertake to ensure they produce meaningful results.

Using an LLM as a chatbot, I've always stood inbetween a response and the next action. At work, there hasn't been a big push for agentic workflows and so I still find myself coding a lot by hand, but I feel like I'd be doing myself more damage then good by not picking up the skills that I need to move with the times. So let's do that today, let's build an agent with Ollama and Spring AI.

## I've incoporated LLM calls in my workflows before, but how is that different from an agent? ##

In my previous RAG project, I created a small RAG tool to learn more about how the retrieval augmentation process works for large language models (LLM) and why context matters. I coded it from scratch utilizing helper agorithms to assist with context chunking and embedding to really learn how RAG systems work under the hood. 

[Read more about that project in this blog post]()

The project was built as a POC tool to read internal documents from slack messages/confluence, and provide internal users with relevant results based on the available context. I explored topics like semantic search and keyword search to refine LLM responses. 

## How are Agents different? ##

In a regular LLM call, my service logic decides what to do:

- call the model
- get the response
- maybe parse it
- maybe call a service

But with an agent, I'mm handing that orchestration to the model. I am defining the tools that the agent will use to act on the prompt it's given and the model decides:

- Do I need to call a tool to answer this?
- which tool?
- what arguments?
- Do I need to call another tool after seeing the result?

My code exposes those tools and starts the conversation, but I am essentially handing off the work to the model.

I'm thinking the sky is the limit here, and picturing a workflow that an Agent would jusut completely take over with my integration work

- Read the description of a JIRA
- Use a skill (index'd .md of the codebase)
- Analyze required components and make the necessary code changes

Maybe even a step further,

- Draft a PR with the modified code and a summary of the changes in correlation to the requirements of the ticket
- Then I review the code changes before the final step (jk I auto approve it, double jk I would never do that)

Seems exciting, but let's start simple.
